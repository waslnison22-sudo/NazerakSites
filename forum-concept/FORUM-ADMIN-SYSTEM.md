# NaZerak Forum — полная система продукта и администрирования

Статус: проектный контракт для реализации. Не означает, что функции уже подключены. Все изменения в Supabase требуют сверки фактической схемы, RLS, GRANT, RPC и регрессионных тестов. Production не меняется без отдельного выпуска.

## Визуальная система
Графит #090A0D, поверхности #101217/#151820, основной текст #F5F5F7, вторичный #A8AAB3, акцент #E6374A. Строгая сетка, читаемые заголовки, умеренные поверхности, отсутствие неонового свечения и лишнего стекла. Общие компоненты: breadcrumb, page header, toolbar, badge, avatar+role, action menu, confirm dialog, toast, skeleton, empty/error/permission states. Поддерживать клавиатуру, видимый focus, reduced motion и мобильные hit-area.

## Главная форума
1. Верхняя навигация: бренд, разделы, поиск, уведомления только при наличии backend, профиль/вход.
2. Hero умеренной высоты, заголовок, ссылки на разделы и создание темы (только при разрешении).
3. Иерархия категория → подфорум с описаниями, количеством тем/ответов и последней активностью.
4. Последние обсуждения с префиксами, автором, временем, ответами и последним сообщением.
5. Официальные объявления и обращения отображаются только из реальных данных, без фальшивых метрик.
6. Полезные ссылки на правила, помощь и Discord.

## Список раздела и темы
Breadcrumb, описание раздела, поиск, сортировка по активности/созданию/ответам, создание темы по праву. Строка темы показывает закрепление, закрытие, решение, префикс, автора, ответы и последнюю активность. Обязательны состояния загрузки, ошибки, пустой выдачи и повторной попытки.
В теме: ответ, цитата, ссылка, подписка, закладка, жалоба. Автор может редактировать/удалять собственную тему в рамках правил. Модераторские действия: закрепить, закрыть, скрыть/восстановить, переместить, назначить префикс, отметить решение. Опасные действия — confirm dialog; успех показывать только после подтверждения backend.

## Инструменты оформления текста
Жирный, курсив, подчёркивание, зачёркивание, заголовок, списки, цитата, ссылка, inline code и code block; предпросмотр, отмена/повтор, цитирование, счётчик длины, предупреждение о несохранённом тексте. Не рендерить HTML пользователя напрямую: allowlist форматирования, санитизация ссылок, запрет javascript: и небезопасных embed. Изображения/файлы включать только после настройки storage, MIME allowlist, размера, квот, удаления и проверки доступа. На мобильном редактор не должен выходить за экран.

## Плашки тем
Системные статусы: закреплено, закрыто, скрыто, решено, официальное, перемещено. Они не назначаются пользователем вручную. Префиксы категории (например Вопрос, Обсуждение, Предложение, Жалоба, Заявление, Гайд, Официально) настраиваются администратором. Метка компактная, текст обязателен, цвет не единственный носитель смысла.

## Роли и оформление ролей
Предварительные группы: Игрок, Проверенный участник (если критерии определены), Помощник, Модератор, Старший модератор, Администратор форума, Руководитель форума, Главный администратор. У роли есть immutable slug, название, короткое название, описание, валидный HEX-цвет, иконка из allowlist, приоритет, активность, публичность и capabilities. Профиль показывает основную и дополнительные роли. Клиент не может сам выдавать роли.
Управление: создать, редактировать оформление, менять приоритет, выдавать/снимать роль, смотреть журнал назначения, предпросмотр бейджа. Нельзя удалить назначенную роль без безопасного переназначения/архивации.

## Матрица разрешений
Capabilities: topic.create, topic.reply, topic.edit_own, topic.delete_own, topic.pin, topic.lock, topic.hide, topic.move, topic.prefix; post.hide, post.restore; report.view, report.resolve, report.assign; role.view, role.create, role.edit, role.assign, role.revoke; category.create, category.edit, category.permissions; member.warn, member.timeout, member.ban, member.unban; audit.view, settings.manage.
Deny by default. Каждая привилегированная RPC проверяет пользователя, capability, target и переход состояния. UI скрывает недоступные кнопки, но серверная проверка обязательна. Пользователь не может назначить роль с правами равными или выше своих. Защита главного администратора от саморазжалования и блокировки обычным интерфейсом. Изменения ролей, банов, разрешений и решений по жалобам пишутся в append-only аудит.

## Панель управления
Обзор очереди жалоб и недавних событий; жалобы с фильтрами, исполнителем, контекстом и решением; управление темами/ответами; участники и история ограничений; роли и матрица разрешений; дерево категорий и префиксы; журнал аудита; настройки с валидацией. Не показывать фальшивую статистику. Массовые и разрушающие действия требуют подтверждения.

## Профиль
Компактное игровое досье в стиле крупных RP-форумов: аватар, имя, role badges, дата регистрации, статус и разрешённые действия. Вкладки Обзор, Сообщения, Темы, Активность (только при наличии достоверной модели), Информация. Поля: Minecraft-ник, короткая биография, проверенные ссылки. Не выводить приватные поля и токены. Владелец редактирует только разрешённые поля; инструменты модератора отображаются по capability. Состояния: loading, not found, private/restricted, error, logged out, own/other profile.

## Supabase и безопасность
Сверить реальную схему, views, functions, triggers, grants, RLS и вызовы фронтенда до миграций. Существующие forum_roles, forum_user_roles, forum_topics.prefix, is_pinned, is_locked, is_archived и solution_state повторно не создавать. SQL-файл в Git не доказывает, что миграция применена к удалённой БД.
Текущие grants на темы и ответы должны быть проверены: интерфейс не является границей безопасности. Привилегированные действия должны идти через серверные RPC с проверкой capabilities. Добавить негативные тесты для anonymous, участника, модератора, администратора и главного администратора.

## Приёмка
Проверить ширины 320/390/768/1024/1440; отсутствие горизонтального скролла; обработчики всех видимых кнопок; keyboard-only/focus/reduced motion; positive и negative test на каждое capability; защиту от подделки ролей через API; санитизацию XSS; регрессию OAuth, форума, профиля и кабинета. Интегрировать по одному маршруту, миграции делать additive с rollback-планом, CI должен быть зелёным, PR остаётся draft до проверки.
