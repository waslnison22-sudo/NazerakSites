# NaZerak — архитектура личного кабинета

## Цель

Личный кабинет — компактная приватная зона игрока, а не административная панель и не дублирование главной страницы. Каждый экран должен отвечать на одну задачу и показывать только реально доступные данные.

## Текущее состояние

- **Вход:** Supabase Auth с Discord OAuth. Клиент использует только публичный publishable key.
- **Идентичность:** auth.users — источник идентификатора аккаунта.
- **Профиль:** public.profiles, ключ id связан с auth.users.id. Пользователь читает и меняет только собственную запись согласно RLS.
- **Minecraft:** сейчас хранится только введённый ник. Это не проверка владения Minecraft-аккаунтом.
- **Медиа-заявки:** таблица public.media_applications существует и защищена RLS. Пользователь может видеть только собственные заявки; приём через сайт пока отключён.
- **Рассмотрение:** нет панели команды, уведомлений модераторов или безопасного интерфейса смены статуса. Поэтому нельзя обещать, что запись из БД увидит команда или что заявка будет рассмотрена.
- **Форум:** отдельный будущий продукт; кабинет не должен притворяться форумом или показывать несуществующие функции.

## Структура интерфейса

1. **Вход:** одна короткая карточка Discord.
2. **Аккаунт:** имя и аватар Discord, короткий статус подключения и выход.
3. **Игровой профиль:** Minecraft-ник и сохранение.
4. **Медиа-партнёрство:** компактный закрытый раздел. Внутри — честный статус доступности, ссылка на официальный Discord и история прежних заявок, загружаемая только при открытии.
5. **Общие состояния:** loading, guest, signed-in, config/error. Ошибка необязательного запроса не должна скрывать подтверждённый аккаунт.

Не показывать в обычном профиле UUID, технические даты, серверную статистику или декоративные карточки, не помогающие игроку выполнить задачу.

## Поток авторизации

1. Загрузить конфигурацию и фиксированную версию Supabase JS.
2. Создать browser client с PKCE, сохранением сессии и автообновлением токена.
3. Подписаться на auth-события до первичного чтения сессии.
4. Проверить сессию с ограничением времени.
5. Показать кабинет сразу после подтверждения пользователя.
6. Догружать профиль отдельно. Ошибка/таймаут чтения не должна трактоваться как отсутствие строки и запускать INSERT.
7. Асинхронные обновления проверяют актуальный ID пользователя и номер рендера.
8. Logout завершает только локальную сессию и возвращает на главную.
9. OAuth redirect должен точно совпадать с разрешённым URL в Supabase.

## Модель безопасности

- Browser client не получает service_role или secret key.
- RLS включён для каждой exposed-таблицы.
- profiles: SELECT/UPDATE/INSERT ограничены auth.uid() = id.
- media_applications: пользователь читает только собственные строки и может создавать только запись со своим user_id. Клиенту не выдаётся UPDATE статуса.
- Роль модератора нельзя брать из редактируемого user_metadata.
- Не добавлять публичную админскую политику и не открывать всем authenticated пользователям чтение/обновление всех заявок.

## Следующие этапы

### Этап 1 — кабинет игрока
- Упростить интерфейс.
- Устранить бесконечные состояния загрузки, race conditions и потерю разметки кнопок.
- Ограничить запросы по времени и показывать отдельные ошибки данных.
- Проверять desktop/mobile и реальную публикацию GitHub Pages.

### Этап 2 — очередь рассмотрения медиа-заявок
- Определить конкретных ответственных и способ администрирования.
- Реализовать серверную точку доступа (предпочтительно Supabase Edge Function) с проверкой JWT и доверенной роли из app_metadata/серверной конфигурации.
- Хранить статус и историю действий; обеспечить переходы pending → reviewing → approved/rejected.
- Отправлять уведомления только после подтверждённого успешного сохранения.
- Не передавать service key в браузер.
- После тестов включить форму подачи. До этого intake остаётся закрытым, чтобы заявки не терялись без ответственного.

### Этап 3 — проверка Minecraft
- Выбрать механизм доказательства владения, например одноразовый код, выдаваемый игровым сервером.
- Подтверждать статус только серверным компонентом после фактической проверки.
- Не доверять полю, которое игрок может изменить сам.

### Этап 4 — релиз
- Статические QA, runtime smoke, browser smoke на desktop/mobile.
- Проверка OAuth от начала до callback и сохранённой сессии.
- Проверка RLS на собственные/чужие записи и запрещённые действия.
- Проверка ошибок сети, таймаутов, повторов и обновления страницы.
- Проверка опубликованных HTML/JS/CSS и cache-busting после deploy.
