# NaZerak — архитектура личного кабинета и заявок

## 1. Принцип

Личный кабинет — не второй сайт и не админ-панель. Это короткая приватная зона игрока, где есть только три пользовательские задачи:

1. войти через Discord;
2. сохранить игровой Minecraft-ник;
3. посмотреть состояние медиа-партнёрства, когда этот процесс действительно подключён.

Никаких серверных характеристик, UUID, технических дат, декоративной статистики и неподключённых действий в обычном кабинете нет.

## 2. Кабинет v3

Порядок экрана:

**Discord → Minecraft → Медиа-партнёрство**

### Discord

- аватар;
- имя;
- короткий статус подключения;
- выход.

### Minecraft

- одно поле ника;
- сохранение;
- честный статус: ник пока не подтверждает владение аккаунтом;
- отдельный retry только если профиль не удалось загрузить.

### Медиа

По умолчанию это одна компактная закрытая строка.

При раскрытии:

- текущая доступность приёма;
- официальный способ связи;
- история собственных заявок, если они когда-либо были приняты системой.

Пока очереди рассмотрения нет, **форма подачи отсутствует полностью**.

## 3. Авторизация

Источник идентичности — Supabase Auth.

Поток:

`Discord OAuth → Supabase Auth → session → кабинет`

Browser client использует только publishable key.

Требования:

- PKCE;
- `persistSession: true`;
- `autoRefreshToken: true`;
- `detectSessionInUrl: true`;
- `onAuthStateChange` регистрируется сразу после создания клиента;
- первоначальный `getSession()` имеет таймаут;
- OAuth redirect всегда ведёт на чистый `cabinet.html`;
- дополнительные точки возврата хранятся отдельно в sessionStorage.

Ни один необязательный запрос профиля не может заблокировать отображение подтверждённого аккаунта.

## 4. Данные

### auth.users

Источник пользователя и Discord identity.

### public.profiles

Минимальная пользовательская запись:

- `id`;
- `minecraft_username`;
- `created_at`;
- `updated_at`.

RLS:

- пользователь читает только себя;
- создаёт только запись со своим `id`;
- изменяет только себя;
- браузер не получает service/secret key.

### public.media_applications

Это **не очередь сама по себе**.

Таблица становится рабочей только после появления:

- ответственного процесса;
- модераторского интерфейса;
- уведомления о новой заявке;
- понятных статусов;
- истории действий;
- серверной проверки прав.

## 5. Медиа-заявка: правильная будущая архитектура

Когда приём будет включён:

`Кабинет`
↓
`защищённая server/Edge Function`
↓
`проверка JWT + серверной роли`
↓
`media_applications`
↓
`уведомление команде`
↓
`модераторская очередь`
↓
`pending → reviewing → approved/rejected`
↓
`история в кабинете игрока`

Браузер **не получает право менять статус заявки**.

Роль модератора нельзя брать из редактируемого `user_metadata`.

До появления этой цепочки кнопка отправки не должна существовать.

## 6. Что происходит сейчас

Сейчас:

- Discord-вход — через Supabase;
- Minecraft-ник — можно сохранить;
- медиа-приём через сайт — выключен;
- заявка через сайт никуда не отправляется, потому что формы нет;
- для связи по партнёрству используется официальный Discord;
- существующая история `media_applications` показывается только внутри раскрытого блока и только владельцу записей по RLS.

Это намеренно лучше, чем принимать заявку в таблицу, которую никто не обслуживает.

## 7. План развития

### Этап A — стабилизация кабинета
- закончить v3 UI;
- убрать бесконечные loading;
- bounded requests;
- OAuth callback/session smoke;
- mobile/desktop smoke;
- RLS smoke;
- проверка опубликованных GitHub Pages assets.

### Этап B — Minecraft verification
Выбрать серверный способ доказательства владения ником.

Пример:

`кабинет → одноразовый код → Minecraft-сервер → проверка → verified`

Нельзя считать ник подтверждённым только потому, что пользователь ввёл его в поле.

### Этап C — media queue
- Edge Function;
- роли команды;
- очередь;
- статусы;
- audit log;
- уведомления;
- retry/error handling;
- RLS regression.

Только после этого включается форма.

### Этап D — форум

Форум остаётся отдельным продуктом.

Кабинет не должен копировать форум, сообщения или модераторские функции.

## 8. QA-гейты

Каждый релиз проверяет:

- anonymous cabinet → guest;
- OAuth start → exact redirect;
- signed-in cabinet → user;
- profile timeout → кабинет остаётся рабочим;
- profile RLS error → нет ложного INSERT;
- media history timeout → кабинет остаётся рабочим;
- media section закрыт по умолчанию;
- нет формы media intake до готовности очереди;
- logout → локальная сессия очищена;
- desktop/mobile → без горизонтального overflow;
- все кнопки имеют текст/ARIA label;
- опубликованные CSS/JS версии совпадают с HTML;
- GitHub Pages действительно отдаёт текущий asset;
- Supabase anonymous Data API не раскрывает таблицы.

## 9. Правило проекта

**Не создавать интерфейс для функции, которую backend ещё не умеет безопасно и гарантированно обслуживать.**

Это относится прежде всего к медиа-заявкам, Minecraft verification и будущей модерации.
